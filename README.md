# 🐳 BackDock - Backup and Restore Docker containers + Remnawave

Интерактивный инструмент для полного бэкапа и восстановления Docker-стеков (заточен под Remnawave, но работает с любыми docker-compose проектами). Запускается локально на твоём ПК, подключается к серверам по SSH — никакие файлы самого скрипта на серверах не остаются.

---

## Возможности

- 📦 **Полный бэкап**: docker-compose проект (yml + .env), bind-mount пути, именованные тома, PostgreSQL (`pg_dumpall`), Docker-образы, crontab, сети, UFW-правила
- 🌟 **Remnawave-пресет**: автоматически находит и предлагает контейнеры панели/ноды/бота одной кнопкой
- ♻️ **Восстановление** с выбором режима (всё / только приложения / без SQL / только системное), с автосохранением конфликтующих файлов (`*.restobak_ДАТА`)
- 🛰 **Умный транспорт**: rsync с прогресс-баром, если он есть на обеих сторонах, иначе fallback на `ssh+cat`
- 🔒 **Контрольные суммы** (sha256) — проверка целостности архива после передачи
- 🖥 **Управление серверами** прямо из меню, включая импорт хостов из `~/.ssh/config`
- 👤 Работает и с root, и с обычным пользователем через беспарольный `sudo`

---

## Требования

**На твоём ПК:**
- `bash`, `ssh`, `tar`
- `rsync` (опционально, скрипт попробует поставить сам при первом запуске)
- Настроенный SSH-доступ к серверам (ключи, алиасы в `~/.ssh/config`)

**На серверах:**
- Docker (Docker Compose v2, если используются compose-проекты)
- Беспарольный SSH-вход (по ключу)
- Если не root — беспарольный `sudo` для docker-команд

## Установка

```bash
chmod +x backdock.sh
./backdock.sh
```

При первом запуске автоматически создастся `config.conf` рядом со скриптом со значениями по умолчанию.

---

## Быстрый старт

1. Запусти `./backdock.sh`
2. Пункт **4) Управление серверами** → добавь сервер (алиас из `~/.ssh/config`) или импортируй сразу все хосты
3. Пункт **1) Сделать бэкапы** → выбери сервер → выбери контейнеры (Enter = все, `r` = только Remnawave-компоненты)
4. Готовый архив окажется в `backups/<сервер>/`

Восстановление — пункт **2)**, выбираешь архив и целевой сервер (можно на другой, не обязательно исходный).

## Конфигурация (`config.conf`)

| Параметр | По умолчанию | Что делает |
|---|---|---|
| `SERVERS` | `()` | Список SSH-алиасов серверов |
| `BACKUP_ROOT` | `backups` | Куда складывать архивы (относительно папки скрипта) |
| `REMNAWAVE_PRESET` | `remna\|caddy\|postgres\|xray\|nginx` | Regex для автовыбора Remnawave-контейнеров |
| `SYS_PATHS` | см. ниже | Системные пути, которые бэкапятся дополнительно |
| `SAVE_IMAGES` | `1` | Сохранять ли Docker-образы целиком в архив |
| `TRANSFER` | `auto` | `auto` (rsync/ssh+cat) или `force-cat` |
| `PAUSE_CONTAINERS` | `0` | Ставить ли контейнеры на паузу во время снятия томов |
| `KEEP_BACKUPS` | `0` | Сколько последних архивов хранить (`0` = все) |

**`SYS_PATHS` по умолчанию:**
```
/var/www:/etc/letsencrypt:/root/.acme.sh:/etc/nginx:/etc/cron.d:/var/spool/cron:/etc/systemd/system:/etc/ufw
```

---

## ⚠️ Про `SAVE_IMAGES`

Включён по умолчанию **намеренно**, не просто так. Если бэкап без образов, при восстановлении Docker скачает **текущий** тег из registry (`:latest`, `:3` и т.п.) — а не ту версию, что реально работала на момент бэкапа. При выходе несовместимого мажорного обновления (как было при переходе Remnawave v2.x → v3.x с изменением API) это может сломать восстановленную систему вместо того, чтобы её спасти.

Отключай (`SAVE_IMAGES=0`) только если точно понимаешь последствия и специально хочешь получить свежие образы при восстановлении.

---

## ⚠️ Про `Docker Pause`

Спрашивается при каждом бэкапе (`y/N`). Замораживает контейнеры на время снятия томов ради консистентности сырых файлов.

Если в стеке уже есть логический дамп БД (`pg_dumpall` — снимается автоматически при наличии Postgres-контейнера в выборе), эта пауза избыточна для целостности данных, но **обрывает live-трафик** на несколько секунд (актуально для VPN-нод, где через контейнер идут активные соединения). В большинстве случаев можно смело отвечать `N`.

## Про rootless Docker

Если SSH-пользователь не root и docker требует `sudo`, скрипт автоматически определяет это (`probe_wrap`) и добавляет `sudo -n` ко всем docker-командам на сервере. Нужен настроенный **беспарольный** sudo для этого пользователя.

Снятие томов в rootless-режиме идёт через вспомогательный контейнер (`alpine`/`busybox`) с `tar`, а не через прямое чтение `/var/lib/docker/volumes/...` (туда нет доступа без root).

---

## Восстановление — режимы

| Режим | Что делает |
|---|---|
| 🌍 **Всё** | Файлы, тома, SQL, запуск стеков + системные пути (nginx, certs, ufw, cron...) |
| 🐳 **Только приложения** | Compose-проекты, тома, SQL, запуск — без системных путей |
| 🐳 **Без SQL** | Как выше, но без импорта дампа (данные берутся только из тома) |
| 🧩 **Только системное** | Только `/etc/nginx`, `/etc/letsencrypt`, `/etc/ufw` и т.д. — без Docker |

Восстановление root-путей (`rootfs`) сохраняет конфликтующие файлы как `путь.restobak_ГГГГММДДЧЧММСС` — ничего не удаляется молча.

## Структура архива

```
backup_ИМЯХОСТА_ДАТА.tar.gz
├── meta/
│   ├── manifest.txt          # сводка: что, когда, откуда
│   ├── containers.tsv        # список контейнеров
│   ├── projects.tsv          # compose-проекты (путь, конфиг, БД)
│   ├── mounts_all.tsv        # все точки монтирования
│   ├── crontab_root.txt
│   ├── ufw_status.txt        # читаемый дамп правил firewall
│   ├── networks.json
│   └── container_*.json      # полный inspect каждого контейнера
├── rootfs/                   # bind-mount пути + SYS_PATHS, как есть на диске
├── volumes/                  # именованные тома, по одному tar.gz на том
├── db/pg_all.sql.gz          # pg_dumpall, если найден Postgres
├── images/                   # docker save, если SAVE_IMAGES=1
└── logs_*.txt                # последние 200 строк логов каждого контейнера
```

## Известные ограничения

- Серверы без полноценного SSH-доступа (например контейнерные хостинги с урезанной панелью управления вроде h1cloud.net) — этим инструментом не бэкапятся, нужен ручной SFTP
- На абсолютно новый/пустой сервер перед восстановлением нужно вручную поставить Docker и Docker Compose — скрипт это не делает
- Восстановление системных путей (`rootfs`) — это прямая перезапись файлов на диске новой машины; при сильно отличающемся дистрибутиве/версии ОС от исходного сервера возможны конфликты (особенно для `/etc/systemd/system`)
